One chat template, and a parser that reads what it teaches

The operator repeated the same failed call forever because it was never shown
the result. Two halves of one defect.

The local lane rendered with whatever template the checkpoint shipped.
~/.modelz/4B carries the older Qwen3 template, which teaches a JSON tool call
inside <tool_call> and renders results its own way; other checkpoints carry
others. One agent talking to several checkpoints through one parser has to
render ONE protocol or the loop desynchronises — the model emits a form nothing
reads, the harness returns no observation, and the next winding repeats the last
action with nothing new in front of it.

framework/templates/qwen_tool_chat_template.jinja is now that one protocol, and
it is authoritative over any template a checkpoint ships. Tool calls go out as
<tool_call><function=NAME><parameter=K>V</parameter></function></tool_call> and
results come back inside <tool_response> in a user turn, which is what the model
actually reads. Rendered a full loop through it: the observation lands in the
prompt.

The parser only understood the JSON form, so with the correct template nothing
at all would have parsed. It reads the function/parameter form now, taking a
parameter value as JSON when it parses as JSON and as text otherwise — a path or
a command is text. The old JSON form is still accepted so a checkpoint mid
migration keeps running.

Also here: file_read on a directory answers with the LISTING and names the verb,
rather than returning a bare error. An error with no remedy re-enters THINK with
no new information, which is how four identical windings happened even after the
verifier started reporting the failure honestly.

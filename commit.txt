Number the lines file_read returns

file_read takes a 0-indexed offset and reported 1-indexed line numbers in its header,
then handed back bare text. The caller had to derive line numbers itself, from a header
in one convention for an argument in the other, while grep -n and sed — the tools it
would use next — are 1-indexed.

That is what broke the kernel build. A specialist read at offset=237, saw "lines
238-262", and edited with `del lines[237:259]`. The deletion landed one line off, leaving
a stray closing brace and a duplicated doc comment in iuft_qc.rs, and the compile failed
with "unexpected closing delimiter" pointing at a line the agent had not touched. It then
tried `sed -i '237,239d'` against numbers read from the same header and shifted the file
again.

Every returned line now carries its own 1-indexed number, and the header states both
spans: the sed range and the equivalent python slice. Nothing has to be computed, so the
class of error is gone rather than documented.

Verified against sed -n on the same file: the numbering agrees line for line. Applied to
all four agents carrying this reader.

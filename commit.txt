The parser threw away a tool call that was actually there

Qwen3.5-27B, reasoning on, asked to review a directory: it reasoned, then wrote
a well-formed call to file_read with all three parameters — and the harness
handed the monologue back as the answer. Two defects, both in the parsing, and a
budget that caused the first.

The template PREFILLS `<think>\n` at the end of the prompt when reasoning is
enabled, so the model's output begins INSIDE the block and carries only the
closing `</think>`. The extractor looked for a matched pair, found none, and left
the entire monologue in the content. An unpaired closing tag is the normal case
here, not an edge one. A block opened and never closed — the generation running
out mid-thought — is all reasoning and no answer, and is treated as such.

`</tool_call>` was required. The model stopped after `</function>`, so the regex
did not match, `tool_calls` came back empty, and the loop read the leftover text
as a conclusion. The closing tags are optional now at all three levels —
tool_call, function, parameter — because a call cut short still says which tool
it wants and with what. Replayed against the exact output from the transcript:
reasoning separated, file_read recovered with path, offset and limit.

And the budget was 4096, set when reasoning was off. Now the reasoning and the
call share it, and a 27B spends most of it thinking before it writes the call —
which is what cut the block before its closing tag. Default is 32768, Qwen's own
figure for an ordinary query, overridable with IG_MAX_TOKENS.

The parameter-name regex could not match `>`

The ⊙perator was right every time. It sent imscribe_system with all twelve marks,
including `>_val`, and the harness ate exactly one of them: my parameter-name
pattern was `[^>\s]+`, which cannot match a name that STARTS with `>`. The
parameter vanished without trace, the tool correctly reported `>` blank, the
⊙perator re-sent the same correct call, and that ran nine windings deep.

The twelve marks are parameter names in this grammar, so `>_val` and `<_val` are
ordinary keys. The name now runs to the angle bracket that CLOSES the tag rather
than to the first `>` in the text. Replayed against the exact call from the
transcript: both `>_val` and `<_val` arrive.

And a guard for the shape of it, whatever the cause: the same call failing the
same way three times gets told so, with its own arguments and error quoted back,
and is forbidden from being re-sent unchanged. Repeating "fix the error and try
again" a fourth time carries no new information — a loop only the harness can see
is a loop only the harness can break.

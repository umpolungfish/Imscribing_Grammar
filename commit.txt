Tool-call arguments reach the template as a mapping

Winding 1 died with "LLM connection failed: Can only get item pairs from a
mapping" — a Jinja error wearing a connection error's name. The template
iterates a tool call's arguments with |items, and on the wire `arguments` is a
JSON STRING: that is the OpenAI convention and the HTTP lane needs it that way.
So the first winding worked, and the second — the first one with a prior tool
call in its history — could not render at all.

The conversion happens at the boundary now, where the message list is handed to
the template, leaving the canonical list in the wire format it has to keep. A
call whose arguments will not parse renders with none rather than taking the run
down: the template guards on `is defined`.

Rendered the exact turn that crashed: the assistant's file_read call comes back
in the function/parameter form, the directory listing lands in a <tool_response>,
and the next assistant turn opens its think block.

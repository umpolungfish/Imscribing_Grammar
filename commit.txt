Parameter types come from the tool's schema, which is what qwen_xml means

I had been hand-rolling a parser against a format that has a specification. The
model card names it: --tool-call-parser qwen3_coder. vLLM delegates that to
xgrammar, whose builtin structural tag for qwen_3_5 / qwen_3_coder gives the
grammar exactly:

  begin  <tool_call>\n<function=NAME>\n
  end    \n</function>\n</tool_call>
  content  JSONSchemaFormat(json_schema=<the function's parameters>,
                            style="qwen_xml")
  reasoning  AnyText ending </think> then \n\n

The last two lines are the ones I had wrong. Parameters are encoded as the
FUNCTION'S OWN JSON SCHEMA, so the declared type is the authority; guessing from
the text — try json.loads, keep a string on failure — is wrong in both directions
and silently. A string parameter holding "123" became the number 123. A string
holding "true" became a boolean. A boolean written by the chat template as "True"
stayed the string "True", because Jinja's `| string` of a Python bool is not JSON.
The template's serialiser is the other half of the same rule: `| tojson` for
mappings and non-string sequences, `| string` for everything else — so JSON is
expected only where the schema says object or array, and that is now the only
place it is parsed.

Checked: a string "123" stays a string, an integer parameter becomes an int, a
boolean written "True" becomes True, an object parses, and a value that does not
fit its declared type is passed through as written for the tool's own validator
to reject. Full parse against the canonical layout returns
file_read(path="/home/x/f.md", offset=0).
